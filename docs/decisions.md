# 方針決定・実現可能性レビュー

## MQTT ブローカー構成

- **決定**: Mosquitto をインストーラに同梱し、Windows サービスとして登録・自動起動する。
- **理由**: 想定ユーザの IT リテラシーが高くないため、ブローカーの個別インストールを要求しない構成にする。
- アプリ本体は MQTT Publisher（必要に応じて Subscriber）のみを担い、ブローカー実装は持たない。

## MQTT Subscriber / モニタ UI

- **決定**: MQTT Subscriber は本体の基本機能として実装し、broker を直接 subscribe する。
- **決定**: UI 導線は `ログ` ページではなく、ダッシュボードから起動する専用モニタウィンドウを採用する。
- **理由**:
  - 現場運用ではダッシュボードから即座に開けて、MQTT Explorer に近い見え方で確認できる方が分かりやすい。
  - MQTT Explorer 相当の軽量確認機能が目的であり、別プロセス化より本体同居の利便性が高い。
  - 監視対象は Tag Bus ではなく broker とし、実際に publish された形を確認できるようにする。
  - broker 状態確認のため `$SYS` を同時に見られる必要がある。

- **実装ルール**:
  - Publisher と責務を混ぜず、`subscribers/` モジュールを新設する。
  - 初期実装は単一 monitor セッション + 直近メッセージのリングバッファ保持とする。
  - MQTT topic はツリー化して表示する。
  - `$SYS/#` を購読対象に含められるようにする。
  - UI 更新は既存 runtime status と同様、初期はポーリングで構わない。

## タグ定義の永続化方式

- **決定**: TOML ファイルを正本（Source of Truth）とする。
- **理由**:
  - AI エージェントによるタグ定義の自動生成・編集を見据えると、テキストフォーマットの方が扱いやすい。
  - Git 等の差分管理に乗せやすい。
  - SQLite はバイナリで AI/外部ツールからの編集が困難。
- UI はメモリ上のタグ定義モデルに対して編集を行い、保存時に TOML へ書き戻す。
- 外部編集との競合を避けるため、保存前に mtime + ハッシュチェックを行う。

## タグ管理 UI

- **決定**: タグ管理画面はテーブル形式（スプレッドシート風）をメインとする。
- **必須カラム**: タグ名 / データ型 / 単位 / 接続先（ドライバ） / アドレス・フィールド / コメント / スキャン周期 / 有効フラグ。
- **要件**:
  - 行の追加・削除・複製・一括編集・コピー＆ペースト
  - 列ソート・フィルタ・検索
  - CSV / TOML での一括インポート・エクスポート
  - 編集中行のバリデーション表示
  - 大量行（数千〜1万）でも表示可能

## JoyWatcher 接続方式

- **決定**: 既存の Borland C++ サンプルを Rust に移植する方針。
- 注意点:
  - Borland 固有 API がある場合は、純粋な通信ロジック部のみを切り出す。
  - JoyWatcher 側のネイティブ DLL に依存する場合は `libloading` または `bindgen` で FFI バインディングを作成する。
  - C++ 例外を跨がない FFI 境界設計が必要。
  - 同期 API の場合は `tokio::task::spawn_blocking` で隔離する。

## ドライバを個別に開発できる形

- **決定**: 子プロセス + IPC（gRPC / Named Pipe）を採用する。
- ドライバを独立した実行形式（`.exe`）として実装し、ハブ本体とは IPC で疎結合に保つ。
- 登録 UI も本体に組み込まず、別ウィンドウ/別プロセスとして提供する。

## ドライバ通信処理の別プロセス化（確定）

- **決定**: ドライバの「登録UI」と「通信ランタイム」を分離し、どちらも本体外プロセスとする。
- **本体の責務**:
  - DriverProcessManager で子プロセス起動/停止
  - gRPCサーバー提供（`TagRegistrationService` + `DriverRuntimeService`）
  - Tag Bus への反映と MQTT 配信
- **ドライバランタイムの責務**:
  - 起動時に `GetDriverDefinition` で接続設定・タグ定義を取得
  - ポーリング/収集した値を `StreamTagValues` で送信
  - `TagValueMessage` に累積 `io_rx_bytes_total` / `io_tx_bytes_total` を同梱し、本体は差分から通信ドライバ別 I/O（B/s）を算出
- **採用理由**:
  - ドライバ追加時に本体のコード変更を最小化できる
  - ドライバ障害を本体プロセスから分離しやすい
  - UI と通信処理を独立リリースしやすい

## gRPC の運用方針（再発防止ルール）

- **決定**: gRPC サーバーは本体起動中は常時稼働とする。
- **理由**:
  - 登録UIプロセスが本体へ接続するため
  - ドライバ通信ランタイムが本体へ値送信/定義取得するため
- **ランタイム制御コマンドの範囲**:
  - `start_runtime_services` / `stop_runtime_services` は「ドライバ通信処理」と「MQTT配信処理」のみを対象とする。
  - gRPC は対象外（本体終了時のみ停止）。

## 認証・権限管理

- **決定**: 初版では認証なし（管理画面ログインなし）。
- **理由**: 当面の利用環境は単独 PC・限定ユーザの想定。
- 将来的にマルチユーザ / 監査ログ要件が出た時点で追加する。

## オフライン環境

- 妥当。すべてのクレートはローカルでビルド可能。
- `cargo vendor` や社内 crate ミラーの利用を推奨する。

- 妥当。Tauri v2 は Svelte 5 と相性良好。

- 原則 300 行以内を目指す。
- ただし機械的な分割ではなく、責務単位での分割を優先する。

## タグ管理右ペインの接続先プロパティ責務

- **決定**: 接続先プロパティの正本は `driver.settings`（JSON）とし、DriverType 固有の入力 UX はドライバ UI（別プロセス）を主担当にする。
- **決定**: 本体右ペインは共通情報表示（`id` / `driver_type` / `enabled`）と `settings` 要約表示を基本とし、編集は原則ドライバ UI 起動導線を優先する。
- **理由**:
  - JoyWatcher のように PostgreSQL 前提項目（Host/Port/Database/Username）へ適合しない DriverType が存在する。
  - DriverType 追加のたびに本体 DTO/フォームへ固定項目を追加する方式は、保守コストと不整合リスクが高い。
  - ドライバ固有知識（接続テスト、探索、補助入力）をドライバ UI 側へ閉じ込めることで、本体改修を最小化できる。
- **移行方針**:
  - 段階移行とし、既存 PostgreSQL フロー互換を維持しながら、JoyWatcher から固定フォーム依存を解消する。
  - 詳細設計は `docs/driver-property-extensibility-design.md` を正本とする。

## ドライバ候補のマニフェスト駆動ディスカバリ

- **決定**: 接続先ドライバ候補は `driverUiBaseDir` 配下の `driver-manifest.json` を走査して自動生成する方式へ段階移行する。
- **決定**: 本体の埋め込み DriverType 列挙（固定配列）は縮退対象とし、移行期間のみフォールバックとして維持する。
- **理由**:
  - ドライバ追加のたびに本体 UI 側の候補定義を改修する運用を解消するため。
  - ドライバ配布物に自己記述情報（表示名、バージョン、実行ファイル、互換条件）を持たせ、検証可能な形にするため。
  - manifest 不備や互換性不一致を UI/ログで明示し、運用時の切り分けを容易にするため。
- **移行方針**:
  - Phase 1: manifest 仕様導入 + discovery API 追加（既存探索併用）
  - Phase 2: 候補一覧を discovery 結果へ切替
  - Phase 3: 埋め込み列挙を削除し legacy 探索を段階縮退
  - 詳細設計は `docs/driver-manifest-discovery-design.md` を正本とする。
